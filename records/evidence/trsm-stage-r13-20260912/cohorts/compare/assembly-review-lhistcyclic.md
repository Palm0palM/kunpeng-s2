# r13 共享 L 循环调度：实际汇编与原日志审查

作业 **1579673** 的 T10/T14 packed-L 历史累加核生成结果相同，热循环均无栈访存或函数调用。T14 的共享 L 生产者确实生成 `b = tid + 1; b += nthreads`，原 barrier 保留。该调度改变没有带来本轮可晋级的成绩；不能由任务分配方式推断执行时间改善。

本报告独立读取取回的目标汇编、冻结源码与原始日志，未执行题目代码、SSH、编译或哈希。机器可读细节与逐条栈指令见同目录 `assembly-review-lhistcyclic.json`。以下行号均是本轮原始文件的 1-based 行号。

## 产物与生成范围

输入位于 `diagnostics/preflight-results/T10-lhistbarrier-repeat-r13/trsm-panel16.s` 和 `diagnostics/preflight-results/T14-lhistcyclic/trsm-panel16.s`。各自 `commands.txt` 中的实际汇编命令为 `gcc -O3 -fno-fast-math -ffp-contract=off -fopenmp -mcpu=generic -S .../该成员/source/trsm.c`，没有预检二进制使用的 `-finstrument-functions` 或 `-DTEST_*` 参数。汇编中没有 `__cyg_profile` / `trsm_test` 符号，`.ident` 为 GCC 12.3.1。这里审查的是本轮计算节点从原成员源码生成的汇编，不是本机重新编译或插桩测试翻译单元。

冻结 `payload` 源码的函数特征再次检查为：T8 有原 panel16 核、无 packedL16 核；T10/T14 两者都有。冻结 T14 `trsm.c` 与 T10 直接文本比较，差异仅为共享生产循环的一处 `schedule(static)` → `schedule(static,1)`；T14 源码 587–595 行是生产循环，602 行 RHS 消费循环仍为 `schedule(static)`。这是文本审查，不是远程源码传输身份验证。

## packed-L 历史累加热循环

两份汇编中 `solve16x8_panel_packedL_sve` 均在 1032–1552 行，完整函数文本相同。`.L31` 历史循环的实际指令位于 **1080–1116 行**：

| 每个 k 的类别 | 数量 | 具体作用 |
|---|---:|---|
| `ld1rd` | 16 | 从 `x4 + 0..120` 读取并广播 16 个 L 系数 |
| `ld1d` | 1 | 从 `x5` 读取一个 8 列 X 向量 |
| `fmla` | 16 | 更新 16 个独立的行累加器 |
| `add` | 2 | 历史指针增加 128 字节，X 指针增加 64 字节 |
| `cmp` / `bne` | 2 | 按递增 k 进入下一次迭代 |
| **总计** | **37** | 不含标签、对齐和 CFI 指令 |

循环没有 store、`sp`/帧指针访存或 `bl`/`blr`。16 个累加器在进入历史循环前清零，历史指针顺序前进；每个输出按 k 顺序 FMA。随后的 `.L30` 从 1117 行开始执行块内三角求解，不能把其指令算入每个历史 k 的 37 条。实际 direct micro 日志也保留 `ordered_FMA_bitwise=1`。

函数入口 1035 行仍申请 **112 字节 ABI 栈帧**，1035–1045 行保存 x29/x30、x19–x21 和 d8–d15，1490–1513 行恢复；整个函数没有调用。这些入口/返回保存不构成历史热循环 spill。外层 `solve_panel._omp_fn.0` 有自己的 560 字节帧及栈访存；结论不扩大为“整个算子没有 spill”。

## 生产者的实际线程映射

T14 汇编 1595 行调用 `omp_get_num_threads`，1596 行把返回值保存为 `w20`；1597 行读取线程号，1598 行 `add w23,w0,1` 设置首个 block。1609 行生成 `w25 = 16*nthreads`，1610 行把线程数扩展为 `x30`，1611 行把 block 扩展为 `x24`。

生产外循环 `.L94` 结束处，**1715 行 `add w23,w23,w20` 和 1717 行 `add x24,x24,x30`** 明确把 block 增加线程数；1719 行把行起点增加 `16*nthreads`。1599–1603 与 1722–1723 行保留边界判断。因而在 38 线程时，线程 t 处理 `t+1, t+1+38, ... < full_blocks`，这是该目标生成物中能直接追踪的映射。1729 行仍调用 `GOMP_barrier`，在进入消费侧之前同步。

T10 对应 1596–1610 行先读取线程数/线程号，对 `full_blocks-1` 做 `sdiv` 和 `msub`，生成商/余数连续分块；2450–2453 行处理获得额外一个任务的前部线程。2333–2339 行将分块索引变为从 1 开始的 block，2438–2439 行分别将行起点增加 16、block 增加 1。生产完成后转入 1612 行的 `GOMP_barrier`。所以 T10 是连续块区间，T14 是步长为线程数的循环分派。

两者每个历史 k 的生产复制内循环依然是 16 条标量 `ldr d0`、16 条 `str d0`、2 条地址增加及 `cmp`/`bne`，共 36 条：T10 为 2401–2436 行，T14 为 1677–1712 行。T14 在生产外循环 1714、1720 行还有两次栈中地址增量读取，不能以 packed 核无热 spill 推断生产代码没有栈访问。RHS 消费侧仍是连续 static：T10 1629–1645 行、T14 1749–1766 行保留商/余数分派。

上述证据确认调度策略已落入机器代码；本轮没有逐线程打包时间、barrier 等待时间或缓存计数器数据，因此不声称负载均衡已缩短关键路径，也不把静态任务量估算写为实测。
