# AZ independent confirmation template — prepared only

`sep13az-confirmation.py` is a 116-line adaptation of AY's standard grouped lifecycle, with differences retained in `sep13az-confirmation.from-ay.patch`. I checked Python syntax using `ast.parse` on text only. The script and imported lifecycle modules were not executed/imported, no operator was compiled or tested, and no network or experiment creation occurred.

Required binding: root must replace **`AY_JOB_ID=None` with the actual original completed AY job ID**. `bound()` blocks both entry points before configuration loading, network calls or metadata changes while the ID is absent. The fixed independent diagnostic is AX **1591086**, total **80100**, C65 source SHA-256 `a855c14b81c00f3d398ac36c5ece6726e15235f18ebf3fe4746570da25a7f874`.

The intended order is **C58-r16 / C65-r1 / C58-r17**. All three run directories and standard records were absent at preparation and remained absent after the text checks. The existing C65-row7balanced AY source is cloned by standard `experiment.new(parent=...)`, not edited or manually copied. Original creation metadata is saved before extending the candidate to use closing C58-r17 as comparison baseline; `source_parent` and `confirmation_of` retain C65-row7balanced. Every member is checkpointed with unchanged settings and runner.

Before reserving/creating anything, the template requires current confirmed C7/C58-r1, accepted own AX evidence, the original AY complete campaign and all 36 original samples, verified standard records and artifact hashes, and an exact re-computation of both original `e.comparison` results. Both must be eligible and agree with AY's stored candidate and campaign fields. Live successful scheduler status for AX and AY is then required. A single exclusive AZ reservation precedes all new experiments and group upload/submission; failure or uncertainty leaves the reservation, so submit cannot retry.

AZ uses one new three-member group and three full official suites per member, with 38 CPUs, 24576 MiB, one packed NUMA and 1800 seconds. Source, group/order, settings, actual machine/GCC 10.3.1/generic/38 threads, raw artifact hashes, scheduler exits, wrapper exit, all 12 PASS/error-zero samples per member and their parsed medians are checked. All three machine profiles must match within AZ. The two unchanged C7 controls must retain current C7 source. C65-r1's entire four-file source, including runner and benchmark, must equal the initial measured C65 snapshot; this is the basis for reusing the accepted AX evidence.

Only the **new AZ 36 samples** enter its two comparisons. No AY sample is pooled into confirmation. `confirmation_passed` is true only when both fresh comparisons are eligible, otherwise false; all samples and decisions are saved. The shared `e.comparison` rule remains authoritative: total gain strictly exceeds the larger of 1% and all case spreads, with no individual case more than 1% slower. No threshold is changed.

An unsuccessful scheduler/verification path aborts without pretending confirmation passed. Existing scheduler evidence/reservations/records remain; root may fetch the original failed job's logs for diagnosis, but the template does not resubmit or overwrite a failed record. After a numerical comparison, campaign status becomes complete and cannot re-enter `record-compare`. Partial recording can only resume against the same saved AZ group, preserving already passed records. AY records remain read-only. No automatic promotion, ZIP, local computation or reset is implemented.

After actual AY binding and root review, intended outer-logged invocations are `python3 .runs/conv/sep13az-confirmation.py submit --go`, then `python3 .runs/conv/sep13az-confirmation.py record-compare` for that original successful AZ group. Neither command was run during preparation.
