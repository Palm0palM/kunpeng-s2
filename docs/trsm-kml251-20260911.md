# TRSM KML 环境排查与 25.1 独立复验

**同一 T7-diagpanel 最终 ZIP 已在 KML 25.1.0 + GCC 12.3.1 环境解压复跑三轮，9/9 PASS，最大误差 1.11e-15。** 作业 1528027 成功结束，调度器、wrapper 退出码均为 0。它不是比赛指定的 KML 25.2.0 复验。

## 之前为什么显示 KML 不可用

原来检查的是比赛指定目录 `/home/HPC/HPCKit/latest/modulefiles` 和默认头/库搜索路径。该目录不存在，编译器找不到 `kblas.h`，链接器找不到 `-lkblas`。这只说明默认环境未配置成功。

此次把搜索范围扩展到 /opt，发现已有 `/opt/donaudata/donau/HPCKit_25.1.0_Linux-aarch64/package/KunpengHPCKit-kml.25.1.0`。其中是解包后的 `gcclib/` 布局，而模块脚本假定安装后的 `lib/` 布局。显式设置 CPATH、LIBRARY_PATH 和 LD_LIBRARY_PATH 后，可用真实 KML 头文件与多线程 `libkblas.so.25.1.0`，不需要 OpenBLAS 补符号。

第二个问题是默认系统 GCC 10.3.1 的 libgomp 缺少 KML 所需的 `omp_get_supported_active_levels@OMP_5.0.1`。超算已有 GCC 12.3.1 归档，在作业私有目录临时解压并前置 bin/lib64 后解决；未修改系统安装。

## 实际验证

最终作业先确认 38 个分配 CPU 位于单一 NUMA、GCC 12.3.1 的 OpenMP 符号、真实 KML 头文件、DGEMM/矩阵复制符号和 38 线程。按包自带 CPU 映射选择 SME 多线程库；每轮 ldd 检查均解析到该 KML 25.1 动态库与私有 GCC12 运行库，没有 OpenBLAS。

探针的版本字符串报告为 `25.1.0`；`KML_VERSION_QUERY_EXIT=1` 是库 API 返回值的原样记录，不是 shell 进程退出码。探针中的 dladdr 地址落在可执行文件的 PLT，实际动态库来源以每轮保存的 ldd 解析路径为依据。

随后从最终 ZIP 解压的目录原样运行 run.sh 三次，取消 KBLAS_LIB 覆盖，沿用默认 -lkblas。官方 benchmark、输入尺寸、计时区、精度容差 1e-12 均未修改；每个样本是 TEST_RUNS=3 的平均值。

|M×N|三轮平均耗时 ms|跨轮中位数 ms|最大误差|
|---|---|---:|---:|
|512×19968|24.36 / 23.84 / 24.44|24.36|1.67e-16|
|2432×17024|291.20 / 290.92 / 292.77|291.20|2.22e-16|
|17024×512|192.85 / 195.36 / 194.30|194.30|1.11e-15|

合计 509.86 ms 只描述本次单版本复跑。编译器与参考库和优化对照不同，不能用它与 OpenBLAS/GCC10 历史结果计算策略提速。
